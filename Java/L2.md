Java Program Execution, Runtime Architecture, and Developer Tooling: Comprehensive Beginner Study Notes

1. Foundational Vocabulary: Prerequisite Computing Concepts Pre-Explained

In computer science, instructors frequently use technical shorthand that can confuse newcomers. To guarantee that every reader approaches this material with total clarity, every technical term used throughout these notes is defined below in plain, accessible language before exploring the core architecture.

* Source Code: The human-readable set of instructions typed by a programmer using the grammatical rules of a programming language. In Java, these instructions are written in plain text and stored in files ending with the .java extension, such as demo.java.
* Machine Code (Native Binary): The native language spoken by a computer's physical Central Processing Unit (CPU). Machine code consists solely of electrical binary digits—zeros (0) and ones (1)—that tell physical microchip switches whether to turn off or on.
* Bytecode: A specialized, platform-neutral intermediate code format invented for Java. When human-readable Java source code is compiled, it is not turned directly into machine code. Instead, it is translated into bytecode and saved in a .class file (such as Demo.class). Bytecode cannot run directly on physical hardware; it requires a virtual machine to translate it into native binary.
* Virtual Machine: A software program that emulates the behavior of a physical computer. It creates an isolated, simulated computing environment inside the computer's memory where programs can execute safely and uniformly regardless of the underlying hardware.
* Java Virtual Machine (JVM): The specific software engine that loads compiled Java bytecode, translates that bytecode into the host computer's native machine code, manages computer memory, and executes the program.
* Compiler: A specialized software utility that scans an entire source code file written in a programming language and converts it all at once into an executable format. The Java compiler tool is named javac.
* Interpreter: A translation utility that reads instructions one single line at a time, immediately translates each line into machine code, and executes it on the physical processor before moving on to the next line.
* Just-In-Time (JIT) Compiler: A high-speed background optimization engine embedded inside the JVM. While the interpreter runs code line-by-line, the JIT compiler watches for code sections that execute frequently, compiles those "hot" routines directly into native machine code on the fly, and saves them in memory so they execute at peak hardware speed.
* Central Processing Unit (CPU) / Processor: The primary physical electronic chip (the "brain" of the computer) responsible for executing machine code instructions and carrying out calculations.
* Random Access Memory (RAM): The computer's high-speed temporary memory where active programs, running instructions, and variables reside while the computer is operating.
* Terminal / Console / Command Prompt: A text-based screen window where users type written commands to the operating system rather than navigating graphical desktop menus with a mouse.
* Integrated Development Environment (IDE): An all-in-one software application designed for software development. An IDE bundles a source code text editor, file managers, build shortcuts, and debugging utilities into a single workspace. Common examples include Visual Studio Code (VS Code) and IntelliJ IDEA.
* Boilerplate Code: Standardized, repetitive sections of code that must be included in a program to satisfy language rules before writing custom application logic.
* Syntax: The strict grammatical rules governing how keywords, punctuation, and structural symbols must be arranged in a programming language.
* Class: A fundamental organizational building block in Java. Every piece of executable code in Java must reside inside a named class structure.
* Method: A collection of statements grouped together under a specific name to perform an action. In Java, program execution always starts inside a specialized entry-point method named main.
* Class Library: A pre-packaged collection of pre-written code routines provided by Java so that programmers do not need to create routine tasks (such as writing text to a terminal or reading files from disk) from scratch.
* Decompiler: A software tool that performs reverse engineering by analyzing a compiled binary or bytecode file (like a .class file) and reconstructing readable source code. An example built into development tools is the Fernflower decompiler.
* Debugger: A diagnostic development tool that lets a programmer pause a program mid-execution, step through instructions line-by-line, inspect variables, and track down programming errors.
* System PATH / Environment Variable: Operating system configuration settings that list the disk folders where command-line utilities (like javac and java) are installed, allowing them to be run from any terminal directory.
* Sandbox Model: A cybersecurity defense architecture that traps running code inside an isolated software container, preventing untrusted software downloaded from the internet from modifying system files or compromising private data.
* Garbage Collection: An automated memory maintenance system inside the JVM that scans memory for data objects that the running program is no longer using and deletes them to free up RAM.

2. The Software Architecture Hierarchy: Deconstructing JVM, JRE, and JDK

In everyday technical conversation, the acronyms JVM, JRE, and JDK are frequently jumbled together. However, they represent three precisely nested tiers of software capability. Rather than separate products, they form concentric layers where each higher tier encapsulates the lower tier and supplies additional capabilities.

The Concentric Layering Model

1. Java Virtual Machine (JVM): The inner core engine. The JVM provides the actual execution environment. It takes compiled bytecode, translates it into the host platform's physical machine language, handles memory cleanup, and enforces runtime security.
2. Java Runtime Environment (JRE): The middle tier required to execute compiled Java software. The JRE encapsulates the JVM and adds the standard Java Class Libraries. The JVM provides the engine, while the Class Libraries supply the pre-written instructions required to interact with the monitor, keyboard, and operating system.
3. Java Development Kit (JDK): The outer tier required by software engineers. The JDK encapsulates the entire JRE (which already includes the JVM and Class Libraries) and adds the development toolchain: the compiler (javac), the interactive debugger, and documentation generators (javadoc).

Comparative Breakdown of Components

Architecture Layer	Internal Components	Core Responsibility	Primary User
JVM (Java Virtual Machine)	Interpreter, JIT Compiler, Garbage Collector, Memory Manager	Executes bytecode, converts instructions to native machine binary, enforces security sandbox	Automated runtime component
JRE (Java Runtime Environment)	JVM plus Standard Java Class Libraries (java.lang, java.io, etc.)	Supplies everything needed to execute an already-compiled .class Java program	End-users and production servers
JDK (Java Development Kit)	JRE plus Developer Utilities (javac, Debugger, JavaDocs)	Supplies everything needed to write source code from scratch, compile, test, and debug software	Software developers and engineers

The Concentric Nesting Formula

The architectural relationship is captured mathematically through progressive encapsulation:

\text{JRE} = \text{JVM} + \text{Core Class Libraries}

\text{JDK} = \text{JRE} + \text{Development Tools} = \text{JVM} + \text{Core Class Libraries} + \text{Development Tools}

Understanding this encapsulation explains why installing the JDK on a computer provides everything necessary to develop and run Java programs simultaneously.

3. The Execution Engine: Why Java is Both Compiled and Interpreted

Computer science curricula often prompt students to categorize Java as either a compiled language or an interpreted language. The technically rigorous answer is that Java is both. Understanding this dual nature requires examining the two traditional execution models, analyzing why early Java systems relied on an interpreter, and discovering how modern JVMs combine both techniques into a high-performance hybrid engine.

Traditional Execution Paradigms: Compilers Versus Interpreters

Historically, programming languages fell squarely into one of two camps:

1. The Pure Compiled Approach (e.g., C and C++):
  * Mechanism: A compiler reads the entire source code file before the program is executed. It validates syntax, optimizes instructions, and directly generates a standalone binary file consisting of native machine code (0s and 1s) tailored for that specific CPU and operating system.
  * Benefits: Execution speed is extremely fast because the physical CPU directly consumes native machine code without runtime translation delays.
  * Drawbacks: The compiled binary is rigidly platform-dependent. A program compiled on an Intel Windows computer cannot run on an ARM macOS computer; it must be recompiled separately for each platform.
2. The Pure Interpreted Approach (e.g., Python):
  * Mechanism: An interpreter does not create a pre-compiled binary file ahead of time. Instead, it reads the original source code instruction by instruction, translating each line into native machine instructions on the fly and immediately handing it to the CPU for execution.
  * Benefits: Code is flexible and immediate; developers can modify a script and execute it instantly without compilation delays.
  * Drawbacks: Execution is significantly slower because the CPU must repeatedly wait for the interpreter to parse and translate instructions during runtime.

Java's Two-Stage Pipeline

Java resolves the trade-off between portability and performance by dividing execution into two distinct stages:

* Stage 1: Compilation via javac: The programmer writes source code in a .java file. The Java compiler (javac) scans the entire file all at once, verifies syntax, and compiles it into platform-independent bytecode saved inside a .class file. This stage is pure compilation.
* Stage 2: Execution via the JVM: The host computer's platform-specific JVM loads the .class file. Inside the JVM, an execution engine translates the bytecode into the local processor's native machine code. This stage historically relied on an interpreter, and in modern systems relies on an interpreter working alongside a dynamic compiler.

Because Java relies on a compiler to create bytecode and a virtual machine engine to translate that bytecode at runtime, Java is both compiled and interpreted.

The Historical First-Principles Dilemma of the 1990s

When Java was created in the 1990s, the design team faced an architectural challenge: Why did they put an interpreter inside the early JVM to execute bytecode, rather than compiling bytecode into machine code right away?

The decision was forced by the hardware realities of that era:

* Compounding Latency: Java had already introduced an upfront compilation step to turn .java files into .class bytecode files. If the JVM had to compile that entire bytecode file into machine code a second time before execution, running a program would require two full compilation phases.
* Severe Hardware Limitations: Computers in the 1980s and 1990s had slow microprocessors, extremely limited RAM (frequently measured in single-digit megabytes), and slow mechanical hard drives. Running two full compilation passes on such hardware caused unacceptable lag.
* Immediate User Responsiveness: An interpreter solves startup lag. The moment the program is launched, the interpreter reads the very first line of bytecode, translates it into machine code, and executes it immediately on the CPU. The application appears on screen right away.

The Modern Solution: The Hybrid JIT and Interpreter Architecture

As computing hardware matured—bringing gigabytes of high-speed memory, multicore CPUs, and solid-state drives—the operational bottleneck shifted. The startup delay of compilation was no longer an issue, while the line-by-line performance penalty of interpretation became glaringly noticeable.

Rather than abandoning the interpreter, modern Java engineers introduced the Just-In-Time (JIT) Compiler, establishing an intelligent hybrid engine:

1. Immediate Startup via Interpretation: When a Java application launches, the interpreter immediately begins reading bytecode line-by-line. The program starts instantly with zero warm-up compilation pause.
2. Continuous Profiling: As the program runs, the JVM continuously monitors the execution flow, identifying methods, loops, and routines that are called repeatedly (designated as "hot" code).
3. Adaptive JIT Compilation: The JIT compiler extracts these high-frequency code paths and compiles them directly into optimized native machine code while the program is actively running.
4. In-Memory Native Caching: The resulting native machine code is cached in memory. The next time that method or loop is called, the JVM bypasses the interpreter entirely and runs the native binary directly on the physical CPU at hardware speed.
5. Efficient Handling of Infrequent Code: Code that runs only once or twice (such as initial startup checks) is left to the interpreter, avoiding the memory overhead and time required to compile code that will never run again.

Performance Reality: Java Versus C++

Even with JIT compilation, benchmarks often demonstrate that C and C++ retain a minor edge in raw startup speed and peak execution efficiency. In C++, source code translates directly into native binary in a single step with zero abstraction layers.

Java consciously makes this trade-off. In exchange for a negligible difference in compilation and startup time, Java provides complete cross-platform portability (Write Once, Run Anywhere), memory safety, sandboxed network security, and syntax simplicity.

The Three Foundational Responsibilities of the JVM

The JVM is far more than a simple file translator. It carries three core operational responsibilities:

1. Instruction Translation: Converting platform-independent bytecode into platform-specific machine code through the coordinated balance of the line-by-line Interpreter and the adaptive JIT Compiler.
2. Network Security Enforcement (The Sandbox Model): Running bytecode inside a tightly monitored virtual container. In distributed environments where bytecode can be downloaded across the internet (such as early browser applets), the JVM prevents untrusted code from modifying local filesystems, spying on memory, or executing unauthorized system commands.
Notice the difference:
- The JVM itself runs as a process on your operating system.
- Java bytecode executes under the JVM.
- Historically, sandbox security mechanisms enforced restrictions on what that bytecode could access.
- Java does not normally create a .exe file. It creates a .class file containing bytecode, which the JVM executes using the CPU.
  -  Windows starts the JVM as a process.
  - The JVM loads your Java bytecode.
  -  The JVM requests memory and other resources from Windows.
  - The JVM interprets or JIT-compiles bytecode into machine instructions.
  - The CPU executes those instructions.
3. Automated Memory Reclamation (Garbage Collection): Managing application memory automatically. The JVM continually tracks created data objects, identifies those no longer reachable or needed by the program, and cleans them out of RAM without requiring manual deallocation code from the developer.

4. The Runtime and Tooling Layers: Deep Dive into JRE and JDK

With the JVM's internal architecture clear, the next step is examining how the JRE and JDK provide the external libraries and tools needed to write and run software.

The Java Runtime Environment (JRE): The Power of Class Libraries

A common beginner question is: If the JVM is the engine that converts bytecode into machine code, why can't we simply install the JVM alone to run our software?

The reason is that the JVM is only an execution engine. It understands raw computational instructions (like adding numbers or branching logic), but it has no built-in knowledge of basic operating system interactions—such as drawing text characters on a terminal console, reading files from a hard drive, or opening network sockets.

To make practical programming possible, the Java Runtime Environment (JRE) pairs the JVM with the Standard Java Class Libraries:

* The Problem of Standard Operations: When a programmer writes a basic instruction to display text:

System.out.println("Hello World");


Neither the developer nor the JVM writes the hundreds of low-level lines of code needed to interact with the operating system's console drivers. That functionality is already written, optimized, and bundled inside Java's standard class libraries (specifically within the fundamental java.lang library).

* Cross-Language Analogies:
  * In C++, a programmer includes pre-built input/output libraries by typing #include <iostream> to access std::cout.
  * In C, a programmer includes standard header files by typing #include <stdio.h> to access printf.
  * In Java, these foundational capabilities are organized into pre-compiled classes embedded within the JRE.
* The Execution Requirement: If a computer had a JVM without the JRE's class libraries, any program attempting to print text, read input, or allocate memory structures would immediately crash with missing class errors. The JRE is the minimum package required to execute Java software.

The Java Development Kit (JDK): The Complete Engineering Toolkit

While ordinary computer users only need the JRE to run software, software developers need tools to create programs from scratch. The Java Development Kit (JDK) fulfills this need by wrapping around the JRE and providing developer-facing command-line utilities:

1. The Java Compiler (javac): The essential tool that validates source code written in .java files and compiles it into .class bytecode files.
2. The Java Application Launcher (java): The command that launches the JRE, initializes the JVM, loads the specified .class file, and starts program execution.
3. The Interactive Debugger (jdb): A development tool that lets programmers pause execution at chosen lines of code, inspect variable values stored in memory, and step through instructions line-by-line to find logic bugs.
4. The Documentation Generator (javadoc): An automated documentation tool that scans formatted code comments and generates structured reference manuals for libraries and APIs.

Environment Configuration: Why the System PATH Matters

When installing the JDK, a developer must configure the computer operating system's Environment Variables, specifically the system PATH:

* The Role of PATH: When a user types a command like javac demo.java into a terminal, the operating system does not automatically search every folder on the hard drive. It only looks in the directories listed in the PATH variable.
* Configuration: By adding the JDK's bin (binary) folder to the system PATH, developers can run javac and java from any folder in their terminal window without needing to type the full, complex folder path to the compiler every time.

5. The Java Ecosystem Landscape: JSE vs. JEE (Jakarta EE) vs. JME

To serve different computing sectors—from small electronics to massive global banking servers—Java was organized into three core editions. Understanding the distinctions between these editions helps learners navigate industry terminology.

Comparative Edition Matrix

Java Edition	Full Technical Title	Historical & Modern Role	Core Capabilities	Current Status
JSE	Java Standard Edition	Core Java baseline; fundamental programming foundation	OOP principles, basic I/O, collections, multithreading, standard JVM	Actively maintained; mandatory foundation for all Java work
JEE / Jakarta EE	Java Enterprise Edition	Enterprise web backends, distributed systems, high-volume APIs	Database transaction managers, web servlets, server-side frameworks (Spring Boot)	Actively maintained under the Eclipse Foundation as Jakarta EE
JME	Java Micro Edition	Lightweight runtime for resource-constrained electronics	Scaled-down JVM, minimal memory libraries for early feature phones	Largely obsolete; replaced in the modern market by Android

Detailed Edition Breakdown

1. Java Standard Edition (JSE / Core Java)

JSE is the baseline of the Java world. It encompasses the core syntax, object-oriented programming concepts (classes, objects, inheritance, encapsulation, polymorphism), basic file and console input/output, and standard data structures. Every Java engineer begins by learning JSE.

2. Java Enterprise Edition (JEE / Jakarta EE)

As the internet expanded, enterprises required specialized capabilities to build scalable web applications and manage corporate databases. JEE was created as an enterprise-grade extension on top of JSE:

* It adds enterprise libraries to handle web requests (Java Servlets), manage database transactions, and coordinate distributed corporate software.
* In modern industry practice, Oracle transferred control of JEE to the Eclipse Foundation, where it was formally renamed Jakarta EE.
* Modern enterprise frameworks like Spring Boot build upon these foundational enterprise standards to power large corporate websites and web services.

3. Java Micro Edition (JME)

During the early emergence of cellular phones and smart appliances, microprocessors were weak and memory was measured in kilobytes:

* JME provided a lightweight, stripped-down runtime designed to run basic software and games on early feature phones and cable television set-top boxes.
* With the arrival of modern smartphones, JME lost its commercial relevance. It was replaced by the Android operating system, which uses modern Java syntax and ecosystem tools alongside Kotlin, running on its own dedicated mobile architecture.

6. Step-by-Step Practical Lab: Writing, Compiling, and Executing Your First Program

To ground theoretical concepts into working skill, this lab walks through the exact process of authoring, compiling, inspecting, and executing a foundational Java program using a text editor and the terminal.

The Development Workspace Setup

Beginners should remember that despite the complexity of modern IDEs, Java source code is stored as basic, human-readable text:

1. Create a dedicated project folder on your computer named java-first-program.
2. Open an editor such as Visual Studio Code, a dedicated IDE like IntelliJ IDEA, or even a basic text editor like Notepad.
3. Inside your project folder, create a new file named demo.java.

Writing the Program Code

Type the following standard Java boilerplate code into demo.java:

class Demo {
    public static void main(String[] args) {
        System.out.println("Hello World");
    }
}


High-Level Structural Anatomy

While later course modules explore every keyword in depth, beginners should understand the core roles of these structural elements:

* class Demo: In Java, all code must be enclosed inside a class structure. By convention, class names typically use PascalCase (capitalizing each word).
* public static void main(String[] args): This exact phrase marks the designated entry point of the application. When the JVM launches, it looks specifically for this method to start executing instructions.
* System.out.println("Hello World");: The specific instruction directing Java's standard class libraries to print the text string "Hello World" to the terminal console, followed by a newline.

Step 1: Compiling Source Code with javac

Open your terminal or command prompt and navigate directly into the java-first-program directory where demo.java is saved.

Run the compiler by typing:

javac demo.java


Behind the Scenes of Compilation

1. The operating system finds the javac compiler using the directories listed in your system PATH.
2. The javac compiler reads demo.java entirely, validating every syntax rule.
3. Because no syntax errors exist, the compiler generates a new file in your directory: Demo.class.
4. This .class file contains the platform-independent bytecode. It is an intermediate instruction set designed specifically for the Java Virtual Machine.

Step 2: Understanding Decompilation and the Fernflower Engine

If a developer attempts to view Demo.class in a code editor like VS Code, the editor typically displays readable Java code rather than unreadable binary or bytecode.

This occurs because modern developer tools automatically activate an embedded decompiler (such as the Fernflower decompiler engine). The decompiler reads the intermediate bytecode and reverse-engineers a reconstructed approximation of the original Java source code for viewing. Developers should recognize that the file stored on the hard drive is intermediate bytecode, not standard English text.

Step 3: Executing the Program with java

With the Demo.class file compiled, execute the application by calling the Java application launcher:

java Demo


(Crucial beginner rule: Never type java Demo.class or java demo.java. The java command takes the name of the compiled class, not the file extension).

Behind the Scenes of Program Execution

1. The java launcher initializes the JRE and starts the platform-specific JVM in memory.
2. The JVM loads Demo.class and links the standard Class Libraries containing System.out.println.
3. The JVM's execution engine processes the bytecode:
  * The Interpreter translates the bytecode instructions line-by-line into the native machine code format required by the local processor.
  * If routines were executed millions of times, the JIT Compiler would compile them into native binary for in-memory caching.
4. The host computer's physical CPU executes the native machine code instructions.
5. The terminal displays the resulting output:

Hello World


Complete End-to-End Execution Workflow

1. Authoring Phase: The programmer writes human-readable instructions in demo.java.
2. Compilation Phase: The command javac demo.java invokes the JDK compiler, creating the platform-independent bytecode file Demo.class.
3. Launch Phase: The command java Demo launches the JRE and initializes the JVM.
4. Translation Phase: The JVM links the standard Class Libraries and translates the bytecode into native machine code using its hybrid Interpreter and JIT compiler engine.
5. Hardware Execution: The physical CPU runs the native machine code instructions.
6. Program Output: The terminal window prints "Hello World".

7. Study Habits, Curriculum Guidelines, and First-Principles Learning

A central message of this lecture series is that true engineering competence comes from internal comprehension rather than memorizing superficial syntax. In an era where generative AI models can generate syntax on demand, an engineer's true professional value lies in understanding system architecture, operational mechanics, and first principles.

Guidelines for Active Learning

* Avoid Passive Consumption: Simply watching video lectures creates an illusion of competence. Every code example, terminal command, and environment setup demonstrated in class must be reproduced on your personal computer.
* The Companion Problem Repository: Daily homework problems and practice questions are hosted on the course's companion GitHub repository (linked in the lecture descriptions). Students must regularly pull these exercises and write out solutions by hand.
* The First-Principles Debugging Rule: When encountering an error or stuck on a coding exercise, avoid immediately pasting the error into ChatGPT or Google. Instead, trace the problem systematically:
  * Did the compiler fail during the javac phase (syntax error)?
  * Did the runtime fail during the java phase (missing class or runtime exception)?
  * Is the system PATH properly pointing to the JDK bin folder?
  * Are file and class names matching with correct casing? Working through errors independently builds deep intuition for how computer systems operate.

8. Curriculum Review and Self-Check Assessment

Use these review questions and analytical prompts to test your retention and reinforce active recall.

Part I: Conceptual Review Questions

1. Question: What is the structural relationship between JVM, JRE, and JDK?
  * Answer: They are concentric software layers. The JVM (execution engine) is contained within the JRE (which adds Java Class Libraries). The JRE is contained within the JDK (which adds developer tools such as javac, the debugger, and javadoc).
2. Question: Is Java a compiled or an interpreted language? Explain why.
  * Answer: Java is both. It compiles human-readable source code (.java) into intermediate bytecode (.class) all at once using the javac compiler. It then translates and executes that bytecode at runtime inside the JVM using an interpreter and a JIT compiler.
3. Question: Why did early Java Virtual Machines in the 1990s rely on an interpreter instead of compiling bytecode into machine code right away?
  * Answer: In the 1990s, hardware had slow processors, limited RAM, and slow storage. Since Java already had an initial compilation step to generate bytecode, a second full compilation step at runtime would have caused severe startup delays. An interpreter allowed the program to start executing instructions immediately.
4. Question: How does the JIT (Just-In-Time) compiler work with the interpreter in modern JVMs?
  * Answer: They work as a cooperative hybrid team. The interpreter starts executing bytecode immediately so the program opens without delay. Simultaneously, the JVM profiles the code to identify frequently executed ("hot") sections. The JIT compiler translates those specific hot sections directly into native machine code on the fly and caches them in memory, allowing them to run at full hardware speed.
5. Question: Why is a standalone JVM incapable of running a complete Java application by itself?
  * Answer: The JVM is only an execution engine; it does not contain the pre-written Class Libraries required to perform real-world tasks like displaying text on a console, handling user keyboard input, or accessing disk files.
6. Question: What file is produced after executing javac demo.java?
  * Answer: It generates a platform-independent bytecode file named Demo.class (matching the class name defined inside the source file).
7. Question: What is the Fernflower decompiler, and why does an IDE use it?
  * Answer: Fernflower is a decompiler utility built into editors like VS Code. When a developer opens a .class bytecode file, Fernflower reverse-engineers the bytecode back into human-readable Java code so the developer can inspect it.
8. Question: What trade-off did Java accept regarding execution speed compared to C++?
  * Answer: Java accepted a minor trade-off in startup time and initial compilation overhead compared to C++ in exchange for cross-platform portability (Write Once, Run Anywhere), memory safety, sandboxed security, and clean syntax.
9. Question: What is Jakarta EE, and what was its original name?
  * Answer: Jakarta EE is the modern name for Java Enterprise Edition (JEE). It provides advanced server-side libraries and specifications for high-concurrency web applications, database transactions, and enterprise microservices.
10. Question: Why is Java Micro Edition (JME) no longer widely used today?
  * Answer: JME was designed for early resource-constrained mobile phones and set-top boxes. It was made obsolete by modern smartphones, primarily through the rise of Android, which uses modern Java/Kotlin development on its own runtime platform.
